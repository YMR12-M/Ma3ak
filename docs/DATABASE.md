# قاعدة البيانات

MySQL، مصدر الحقيقة الوحيد هو [`backend/sql/schema.sql`](../backend/sql/schema.sql) - شغّله كامل على قاعدة فاضية وهيبني كل حاجة. ملفات `migration_2_*.sql` و`migration_3_*.sql` تاريخية بس (لترقية قاعدة اتعملت قبل ما `schema.sql` يتحدّث ويشملهم) - **متشغّلش الـ migrations دي على قاعدة اتعملت بـ schema.sql الحالي**، هتفشل (الأعمدة موجودة بالفعل).

## العلاقات (نظرة سريعة)

```
users (patient) ──┬──< patient_caregiver >──┬── users (caregiver)
                   │
                   ├──< medications ──< doses
                   ├──< appointments
                   ├──< vitals
                   └──< notifications >── users (المستلم عبر user_id)

users (أي دور) ───┬──< push_subscriptions    (جهاز واحد لكل صف)
                   └──── notification_prefs   (صف واحد لكل مستخدم)

medications ─────── medication_images         (صورة واحدة لكل دواء)
```

كل جدول (غير `users` نفسه) بيرتبط بـ `users.id` عن طريق `patient_id` مع `ON DELETE CASCADE` - لو مريض اتمسح، كل بياناته بتتمسح معاه تلقائيًا.

## الجداول

### `users`
مريض أو متابع في نفس الجدول (`role` بيفرّق بينهم).

| عمود | النوع | ملاحظات |
|---|---|---|
| `email` | VARCHAR(190) UNIQUE NULL | اختياري - المريض عادة بدون إيميل |
| `password_hash` | VARCHAR(255) NULL | `NULL` للمريض (مبيدخلش بباسورد خالص) |
| `role` | ENUM('patient','caregiver') | |
| `phone` | VARCHAR(30) UNIQUE NULL | معرّف الدخول الأساسي للمتابع |
| `link_code` | VARCHAR(10) UNIQUE NULL | خاص بالمريض - كود قصير لمشاركة متابع تاني |
| `access_token` | VARCHAR(64) UNIQUE NULL | خاص بالمريض - التوكن الطويل في لينك الدخول |
| `recovery_hash` | VARCHAR(255) NULL | كود استرجاع الباسورد، **مهشّور بـ bcrypt زي الباسورد** - إحنا نفسنا مش قادرين نقراه |

**كود الاسترجاع:** بيتولّد وقت التسجيل، بيتعرض للمستخدم **مرة واحدة بس**، وبيتستهلك بعد الاستخدام (بيتولّد واحد جديد مكانه). من غيره المتابع اللي بينسى باسورده كان بيفقد وصوله لكل بيانات مريضه نهائيًا - مفيش إيميل ولا SMS في المشروع.

### `patient_caregiver`
جدول ربط many-to-many. `UNIQUE KEY uniq_link (patient_id, caregiver_id)` يمنع تكرار نفس الربط.

### `medications`
| عمود | النوع | ملاحظات |
|---|---|---|
| `times` | JSON | مصفوفة أوقات نصية، مثال: `["08:00","14:00","20:00"]` |
| `days_of_week` | TINYINT UNSIGNED | قناع 7 بت: بت 0 = الأحد ... بت 6 = السبت. `127` = كل يوم (الافتراضي) |
| `pills_left` | SMALLINT UNSIGNED NULL | كمية الدوا الفاضلة. `NULL` = المتابع مش بيتابع الكمية للدوا ده |
| `low_stock_notified_at` | DATETIME NULL | طابع "تنبيه قرب الخلاص اتبعت" - بيترجّع `NULL` أول ما الكمية تتزوّد |
| `active` | TINYINT(1) | `0` = محذوف منطقيًا (soft delete)، بيفضل في السجل. **كل استعلامات الجرعات بتفلتر `active = 1`** |
| `is_critical` | TINYINT(1) | توقيته مش قابل للتأجيل - بيقفل الغفوة ويرفع أولوية الجرعة الفايتة لـ `critical` |
| `snooze_allowed` | TINYINT(1) | المتابع يقدر يقفل الغفوة لدواء عادي كمان. بيتخزّن `0` إجباريًا لو `is_critical = 1` |
| `has_image` | TINYINT(1) | فيه صف في `medication_images`؟ علم بيخلي القايمة تعرف من غير JOIN ومن غير ما تشحن الصورة |
| `notes` | TEXT NULL | تعليمات الدكتور - بتوصل المريض في شاشة الجرعة وشاشة المنبه |

**ليه `days_of_week` مش مجرد رفاهية:** من غيره كل دواء في التطبيق كان **يومي بالضرورة**، فالأدوية الأسبوعية الشائعة عند نفس الجمهور ده (أليندرونات للعظام، ميثوتريكسات للروماتيزم، حقن ب12) مكانش قدام المتابع فيها غير اختيارين والاتنين غلط: يسجّلها يومي - فالمريض يترنّ عليه كل يوم وتتحسب فايتة 6 مرات في الأسبوع - أو ميسجّلهاش أصلاً.

**ليه فلتر `active = 1` مهم في كل مكان:** إيقاف الدواء بيعمل `active = 0` وبس. من غير الفلتر ده كان المنبه بيفضل يرنّ على المريض لدوا الدكتور وقّفه، والمتابع ياخد "جرعة فاتت" لدوا هو نفسه وقّفه - وكبير السن بياخد دوا موقوف لأن التطبيق قاله. وإيقاف الدوا (أو تغيير مواعيده) بيشيل كمان جرعاته **الجاية** المعلّقة، واللي فات ميعادها بيفضل لأنه تاريخ فعلي والتقرير بيقرا منه.

### `doses`
جرعة واحدة فعلية لموعد معيّن - بتتولّد تلقائيًا من `medications.times` (وبس في الأيام المفعّلة في `days_of_week`) بواسطة `scheduler.js`: النهاردة وبكرة، مرة كل ساعة - وفورًا عند إضافة أو تعديل أي دواء.

| عمود | النوع | ملاحظات |
|---|---|---|
| `status` | ENUM('pending','taken','missed') | `missed` بيتحط تلقائيًا بعد 30 دقيقة من الميعاد بدون تسجيل |
| `snooze_until` | DATETIME NULL | غفوة. **مبيتصفّاش بعد الرنّة** - هو "الميعاد الفعلي" اللي كل مراحل المنبه بتتحسب منه: `COALESCE(snooze_until, scheduled_at)` |
| `snooze_count` | TINYINT | سقفه 3 (`MAX_SNOOZES` في `frontend/js/doseLogic.js`) |
| `snooze_notified_at` | DATETIME NULL | رنّينا لغفوة معيّنة ولا لأ - ده اللي بيمنع تكرار الرنّة كل دقيقة |
| `due_notified_at` | DATETIME NULL | طوابع "اتبعت مرة واحدة بس" |
| `reminder_notified_at` | DATETIME NULL | |
| `escalated_at` | DATETIME NULL | |
| `UNIQUE KEY uniq_dose (medication_id, scheduled_at)` | | بيمنع تكرار توليد نفس الجرعة مرتين (الـ scheduler بيستخدم `INSERT IGNORE`) |
| `KEY idx_status_scheduled (status, scheduled_at)` | | الـ scheduler بيلف على الجرعات المعلّقة كل دقيقة |

**ليه الغفوة بتمدّ فترة السماح:** قبل كده `notifyDueDoses` كانت بتصفّي `snooze_until` بعد الرنّة، وفي **نفس الدورة** `markMissedAndNotify` تشوف الجرعة (ميعادها الأصلي عدّى فترة السماح) وتعلّمها فايتة. النتيجة: موبايل المريض بيقوله "وقت الدوا" وموبايل ابنه بيقوله "فوّتها" في نفس الدقيقة. وكمان 3 غفوات × 10 دقايق = 30 دقيقة = `GRACE_MINUTES` بالظبط، فالرقمين كانوا متعارضين من الأساس.

**ليه طوابع الإشعارات في قاعدة البيانات مش في ذاكرة السيرفر:** Render بينيّم الخدمة المجانية وبيعيد تشغيلها، وأي حالة في الذاكرة بتضيع - يعني المريض كان ممكن ياخد نفس التنبيه تاني، أو ما ياخدوش خالص.

### `appointments`
مواعيد طبية بسيطة - عنوان، دكتور، مكان، وميعاد. `KEY idx_appointment_at (appointment_at)` - الـ scheduler بيقرا الجاي كل دقيقة، ومن غير الفهرس ده كان بيمسح الجدول كله في كل دورة.

### `vitals`
| عمود | النوع | ملاحظات |
|---|---|---|
| `type` | ENUM('blood_pressure','blood_sugar','weight','heart_rate','temperature') | |
| `value_json` | JSON | شكل حر حسب النوع، مثال: `{"systolic":120,"diastolic":80}` أو `{"value":95,"unit":"mg/dL"}` |
| `KEY idx_patient_recorded (patient_id, recorded_at)` | | آخر 100 قراءة لمريض - من غيره الاستعلام بيعمل filesort |

**القراءة الخطرة بتولّد تنبيه حرج:** التحقق في `routes/vitals.js` نوعين مختلفين - `RANGES` بتتأكد إن الرقم **منطقي** (مش 900)، و`CRITICAL_LIMITS` بتتأكد إنه مش **خطر**. القراءة اللي بره الحدود الخطرة بتبعت `patient_issue` بأولوية `critical` لكل المتابعين فورًا. قبل كده المريض كان يسجّل ضغط 200/130 والتطبيق يقبله في صمت، والمتابع عمره ما يعرف إلا لو فتح تاب القياسات بنفسه وبص.

### `notifications`
| عمود | النوع | ملاحظات |
|---|---|---|
| `user_id` | INT | المستلم (مريض أو متابع) |
| `patient_id` | INT | بخصوص أي مريض (حتى لو المستلم متابع) |
| `type` | ENUM(...7 أنواع) | `missed_dose`, `upcoming_appointment`, `general`, `patient_issue`, `dose_due`, `dose_reminder`, `dose_escalation` |
| `priority` | ENUM('critical','normal','info') | `critical` بيخترق ساعات الهدوء وتفضيلات النوع |
| `related_id` | INT NULL | id الجرعة/الموعد المرتبط |
| `dedupe_key` | VARCHAR(120) NULL | مع `UNIQUE (user_id, dedupe_key)` - ده اللي بيمنع التكرار فعلاً |
| `is_read` | TINYINT(1) | المستخدم شافه |
| `handled_at` | DATETIME NULL | المستخدم **اتصرف** - حاجة تانية خالص |
| `push_sent_at` | DATETIME NULL | سجل التوصيل |
| `delivered_at` | DATETIME NULL | بيتسجّل من الـ Service Worker |
| `clicked_at` | DATETIME NULL | |

**منع التكرار اتغيّر من كود لقيد في قاعدة البيانات.** قبل كده `notifyUpcomingAppointments` كان بيعمل `SELECT` بعديه `INSERT` - وده فيه فجوة سباق حقيقية: دورتين scheduler متداخلتين (أو نسختين من السيرفر) كانوا ممكن يقروا "مفيش" في نفس اللحظة ويدخّلوا الاتنين. دلوقتي `INSERT IGNORE` + `UNIQUE (user_id, dedupe_key)`، وهو نفس أسلوب `uniq_dose` الموجود في `doses` أصلاً.

المفتاح مركّب على `(user_id, dedupe_key)` مش على `dedupe_key` لوحده: نفس الحدث (جرعة فاتت) بيروح لأكتر من متابع، والمفروض كل واحد فيهم ياخد نسخته.

### `medication_images`
| عمود | النوع | ملاحظات |
|---|---|---|
| `medication_id` | INT PK | علاقة 1:1 مع الدواء، `ON DELETE CASCADE` |
| `mime` | VARCHAR(40) | `image/jpeg` أو `png` أو `webp` |
| `data` | MEDIUMTEXT | base64 من غير بادئة `data:` |

**ليه جدول منفصل مش عمود في `medications`:** استعلامات قايمة الأدوية بتستخدم `SELECT *` وبتتنادى كل ما الشاشة تتفتح - عمود فيه صورة كان هيتشحن مع كل طلب من غير أي داعي.

الواجهة بتصغّر الصورة لـ 640 بكسل/JPEG قبل الرفع (`frontend/js/medImages.js`)، فالحجم الفعلي عادة 40-80 كيلو. الحد على السيرفر (400 كيلو base64) خط دفاع أخير مش أول.

### `push_subscriptions`
كل صف = متصفح واحد على جهاز واحد وافق يستقبل إشعارات. من غير الجدول ده التنبيه بيموت بمجرد ما المستخدم يقفل التاب.

| عمود | النوع | ملاحظات |
|---|---|---|
| `endpoint` | VARCHAR(500) | عنوان خدمة الدفع، فريد عالميًا - `UNIQUE (endpoint(191))` |
| `p256dh` / `auth` | VARCHAR(255) | مفاتيح التشفير بتاعة المتصفح |
| `user_agent` | VARCHAR(255) NULL | عشان المستخدم يعرف "ده أنهي جهاز" |
| `fail_count` | TINYINT | 5 فشل متتالي = الاشتراك ميت ويتشال |
| `last_success_at` | DATETIME NULL | |

الاشتراكات بتموت لوحدها (المستخدم مسح بيانات الموقع، الجهاز اتغيّر). خدمة الدفع بترد `404`/`410` والصف بيتمسح فورًا - من غير كده الجدول بيتلوث وبنفضل نضرب على عناوين ميتة.

### `notification_prefs`
صف واحد لكل مستخدم، بيتعمل عند أول حفظ (المستخدم اللي لسه معملهوش صف بياخد الافتراضي: كله شغال، من غير ساعات هدوء).

| عمود | النوع | ملاحظات |
|---|---|---|
| `push_enabled` | TINYINT(1) | مفتاح رئيسي - بيقفل الدفع كله **حتى الحرج** |
| `quiet_start` / `quiet_end` | TIME NULL | لازم الاتنين أو ولا واحد. بتأجّل العادي بس |
| `pref_dose_due` | TINYINT(1) | بيغطي `dose_due` و`dose_reminder` |
| `pref_missed_dose` | TINYINT(1) | بيغطي `missed_dose` و`dose_escalation` |
| `pref_appointment` | TINYINT(1) | |
| `pref_patient_issue` | TINYINT(1) | |

## تفاصيل تستاهل انتباه

- **مفيش soft delete على `appointments` و`vitals`** (`DELETE` فعلي)، بعكس `medications` (`active=0`). لو محتاج سجل تاريخي كامل لاحقًا، ده هيحتاج مراجعة.
- **`doses.status` تتغير من الـ scheduler لوحده** (`pending → missed`) من غير أي فعل من المستخدم - لو بتبني عليها منطق تاني، خد بالك إنها مش "قيمة ثابتة" بعد ما تتسجل.
- **الفهارس المضافة:** `doses(status, scheduled_at)` للـ scheduler (بقى بيلف كل دقيقة)، `doses(patient_id, scheduled_at)` لتقرير الالتزام (بيقرا فترة كاملة لمريض)، و`notifications(user_id, id)` للقراية بـ `since`.
- **جدول `notifications` بيتنضّف تلقائيًا:** الـ scheduler بيمسح الإشعارات **المقروءة** الأقدم من 60 يوم كل 6 ساعات. بعد نظام المنبه بقى كل جرعة بتولّد إشعار أو اتنين (~3,600 صف في السنة للمريض الواحد). **غير المقروء بيفضل مهما كان قديم** - اختفاءه معناه إن حاجة حصلت ومحدش عرف بيها أبدًا.
- **`notification_prefs` بتتحكم في الدفع بس، مش في تخزين الإشعار.** الصف بيتخزّن دايمًا مهما كانت التفضيلات - السجل جوه التطبيق لازم يفضل كامل، اللي بيتقفل هو المقاطعة.
