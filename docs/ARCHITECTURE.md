# البنية المعمارية

## نظرة عامة

معاك تطبيق ويب بسيط من طبقتين، بدون build tool في الفرونت إند:

```
┌─────────────────────────┐         ┌──────────────────────────┐
│   المتصفح (Browser)      │  HTTP   │   Express Server          │
│                          │────────▶│   (Node.js)                │
│  React 18 (CDN UMD)      │  JSON   │                            │
│  Babel Standalone        │◀────────│  routes/*.js               │
│  (بيترجم JSX جوه          │         │  middleware/auth.js        │
│   المتصفح مباشرة)          │         │  utils/access.js, codes.js │
└─────────────────────────┘         │  scheduler.js (polling)    │
                                     └──────────┬─────────────────┘
                                                │ mysql2/promise
                                                ▼
                                     ┌──────────────────────────┐
                                     │   MySQL (schema.sql)      │
                                     └──────────────────────────┘
```

نفس سيرفر الـ Express (`backend/server.js`) بيعمل حاجتين: بيسيرف ملفات الفرونت إند الاستاتيك (`express.static`) وبيعرض الـ API تحت `/api/*`. يعني مفيش سيرفر منفصل للفرونت إند، ومفيش build/deploy خطوة إضافية غير `npm install` و`npm start`.

## ليه بدون build tool؟

الفرونت إند بيحمّل React وBabel Standalone من CDN مباشرة في [index.html](../frontend/index.html)، وملفات `.jsx` بتتحمّل زي ما هي (`<script type="text/babel" src="...">`) وبتتترجم لحظة التحميل في المتصفح. الميزة: صفر إعداد، صفر خطوة build، أي حد يفتح الملفات ويشتغل على طول. التكلفة: ترجمة JSX بتحصل في كل مرة الصفحة تتفتح (مش وقت الدبلوي)، وده تكلفة أداء حقيقية لو المشروع كبر - راجع [FEATURES.md](FEATURES.md) للحدود المعروفة.

## قرارات تصميم أساسية

**١. المريض بيدخل بلينك، مش بباسورد.** كبير السن مش المفروض يتعامل مع تسجيل دخول أو باسورد. المتابع هو اللي بيضيف المريض (`POST /api/patients`)، والسيرفر بيولّد `access_token` عشوائي طويل بيتحط في لينك (`/access/<token>`). فتح اللينك ده = تسجيل دخول تلقائي (`POST /api/auth/access`). راجع [API.md](API.md#access-token) و[DATABASE.md](DATABASE.md).

**٢. شاشتين منفصلتين تمامًا حسب الدور.** `app.jsx` بيوجّه المريض لـ `PatientHome.jsx` (صفحة واحدة، بدون تابات، خط وأزرار أكبر) والمتابع لـ `AppLayout` (لوحة تحكم كاملة بتابات). القرار ده في الكود نفسه (`if (user.role === 'patient') return <PatientHome .../>`)، مش شرط CSS.

**٣. متابعين متعددين لكل مريض.** جدول `patient_caregiver` many-to-many - أكتر من ابن/بنت يقدروا يتابعوا نفس المريض عن طريق كود مشاركة (`link_code`)، وكل واحد فيهم بياخد نسخته من الإشعارات.

**٤. الـ scheduler بيشتغل بـ polling كل 5 دقايق** (`setInterval` جوه نفس عملية Node، مش cron خارجي أو queue). بيعمل 3 حاجات: يولّد جرعات اليوم وبكرة من `medications.times`، يحوّل أي جرعة `pending` عدّت عليها فترة سماح (30 دقيقة) لـ `missed` ويبعت إشعار، ويبعت تذكير بمواعيد خلال 24 ساعة. ده كافي لحجم المشروع الحالي، لكنه مش دقيق للثانية ولا موزّع (single point لو السيرفر وقع فترة، الجرعات هتتولد أول ما يرجع).

**٥. تفضيلات الواجهة (الوضع الداكن، حجم الخط) متخزنة في `localStorage` على الجهاز نفسه، مش في حساب المستخدم.** القرار مقصود: موبايل المريض وموبايل المتابع أجهزة مختلفة، وكل واحد له احتياج مختلف (شوف `app.jsx` تعليق `readBoolPref`/`writeBoolPref`).

## نقاط ضعف معمارية معروفة

- **التذكيرات شغالة بس والتاب مفتوح في المتصفح** (Web Audio + Notification API من جوه الصفحة نفسها). مفيش Service Worker ولا Web Push، يعني لو المريض قفل المتصفح مفيش تذكير خالص. أكبر فجوة في المشروع حاليًا.
- **صفر اختبارات آلية** - مفيش unit ولا integration tests. المنطق الحرج (حساب فتح/قفل الجرعة، الصلاحيات) غير مغطى.
- **schema.sql وملفات migration_*.sql مش موثقين كمصدر حقيقة واضح** - schema.sql فيها كل حاجة مدموجة (مناسبة لقاعدة جديدة)، والـ migrations تاريخية بس لترقية قواعد قديمة.
